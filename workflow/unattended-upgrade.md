# Unattended Upgrade Workflow

This file defines the unattended upgrade execution workflow for Razor-PHP.

It must run the maintenance workflow before unattended execution begins.

Use `workflow/description.md` for project context.
Use `workflow/maintain.md` as the maintenance workflow definition.
Use generated maintenance files for the concrete upgrade plan and implementation steps.

## Maintenance workflow bootstrap

Before unattended upgrade execution begins, run the maintenance workflow defined in:

```text
workflow/maintain.md
```

Running the maintenance workflow must create or update the generated maintenance files required for unattended execution.

The maintenance workflow must complete successfully before any maintenance step is executed.

If the maintenance workflow fails, stop immediately and create a failure log under:

```text
workflow/unattended-upgrade-failure.log.md
```

Do not execute maintenance steps if the maintenance workflow did not complete successfully.

## Required prerequisite files

After the maintenance workflow has completed, the following files must exist:

```text
workflow/description.md
workflow/maintain.md
workflow/versions.md
workflow/maintenance-plan.md
workflow/maintenance-scaffold.md
workflow/maintenance-step<index>.md
```

At least one numbered maintenance step file must exist.

If any prerequisite file is missing after running the maintenance workflow, stop immediately and treat the unattended upgrade as failed during bootstrap.

## Attempt limit

The unattended upgrade may run at most five full attempts.

An attempt begins when `workflow/maintenance-step1.md` starts execution.

An attempt ends when either:

* all maintenance steps complete successfully; or
* any step fails and triggers failure handling.

If an attempt fails before the fifth attempt, the maintenance workflow may be run again using the detected failure information, then the unattended upgrade may run the next numbered attempt.

If the fifth attempt fails, stop permanently.

Do not attempt a sixth run.

## Initial-state backup

After the maintenance workflow has completed successfully, but before the first unattended upgrade attempt begins, create a full initial-state backup of every repository file that may be changed by any generated maintenance step.

The initial-state backup must be stored under:

```text
workflow/backups/initial/
```

The initial-state backup represents the repository state before any unattended step execution.

It is the authoritative rollback source if the unattended upgrade fails after the maximum number of attempts.

The initial-state backup must include:

* all files allowed to change by any generated maintenance step;
* a complete `backup-manifest.md` file;
* notes for expected files that did not exist before execution;
* a timestamp or commit reference if available.

## Execution context

Before executing any maintenance step, create one clear execution context from:

```text
workflow/description.md
workflow/maintain.md
workflow/versions.md
workflow/maintenance-plan.md
workflow/maintenance-scaffold.md
workflow/maintenance-step<index>.md
```

The execution context must be loaded once and preserved for the full unattended upgrade run.

Do not re-iterate the full project context for every step.

Each step must be executed within the same accumulated context so previous decisions, validations, fixes, and observed repository state remain available.

Only step-specific instructions should be read again immediately before executing that step.

## Step execution order

Execute maintenance steps in ascending numeric order:

```text
workflow/maintenance-step1.md
workflow/maintenance-step2.md
workflow/maintenance-step3.md
```

Continue until no next numbered step file exists.

Do not skip step numbers.

If `workflow/maintenance-step1.md` and `workflow/maintenance-step3.md` exist but `workflow/maintenance-step2.md` is missing, stop and report the sequence as invalid.

## Backup requirements

Before executing each maintenance step, create a backup snapshot of the files that may be changed by that step.

The backup must be created before any edit is made.

Backups must be stored under:

```text
workflow/backups/step<index>/
```

Each backup directory must contain:

* copies of every file allowed to change by the step;
* a `backup-manifest.md` file listing the copied files;
* a timestamp or commit reference if available;
* notes for files that were expected but did not exist before the step.

If a step modifies files generated by a previous step, back up the current post-previous-step version before applying the new step.

The backup must always represent the state immediately before the current step begins.

## Per-step execution process

For each maintenance step:

1. Read the step file.
2. Confirm prerequisites listed in the step are satisfied.
3. Confirm allowed files and forbidden files.
4. Create the backup snapshot for the files allowed to change.
5. Execute only the actions defined in the step.
6. Do not perform unrelated cleanup.
7. Do not edit forbidden files.
8. Run the validation commands or validation methods defined in the step.
9. Record the result in the active execution context.
10. Continue to the next step only if validation succeeds.

## Validation requirements

After each step, validation must confirm that:

* the intended files changed as expected;
* forbidden files were not modified;
* required generated files exist;
* Dockerfiles remain syntactically valid enough for Docker build parsing;
* GitHub Actions workflow files remain valid YAML where workflows were changed;
* version references match `workflow/versions.md` where concrete versions are required;
* no unsupported PHP major version was introduced;
* no unsupported Debian baseline was introduced;
* no unrelated repository structure was added.

Where practical, validation should include commands such as:

```bash
git diff --check
docker buildx bake --print
```

Additional validation commands must come from the active maintenance step file.

If a validation command is unavailable in the local environment, record that clearly and perform the strongest available static validation instead.

## Failure handling

If any step fails, stop the normal execution flow immediately.

Failure handling depends on the current attempt number.

A failure includes:

* prerequisite mismatch;
* missing expected file;
* edit conflict;
* forbidden file modification;
* failed validation command;
* invalid Dockerfile syntax;
* invalid workflow YAML;
* package compatibility issue;
* version mismatch;
* unexpected repository state;
* any result requiring guessing to continue.

When a failure occurs before the fifth attempt:

1. Stop executing further maintenance steps.
2. Investigate the failure using the current execution context.
3. Compare the failed state against the backup for that step.
4. Identify the likely cause.
5. Identify whether rollback is required.
6. Create a failure report file for the failed step.
7. Re-run the maintenance workflow using the failure report as additional detected-issue input.
8. Regenerate the maintenance plan, scaffold, and step files so the fix is included in the new sequence.
9. Restart unattended upgrade execution from the regenerated step sequence as the next numbered attempt.

When a failure occurs on the fifth attempt:

1. Stop executing further maintenance steps.
2. Investigate the failure using the current execution context.
3. Create a final unattended upgrade log file.
4. Revert all changed files to the initial-state backup.
5. Verify that rollback restored the repository to its pre-run state.
6. Stop permanently.

Do not regenerate maintenance files after the fifth failed attempt.

Do not continue execution after the fifth failed attempt.

## Final failure log

If the fifth unattended upgrade attempt fails, create a final log file under:

```text
workflow/unattended-upgrade-failure.log.md
```

The final log must contain:

* total attempts used;
* failed attempt number;
* failed step file;
* failed action;
* files changed before failure;
* validation command or check that failed;
* exact error output where available;
* failure reports created during all attempts;
* rollback actions performed;
* whether rollback to initial state succeeded;
* files restored from the initial-state backup;
* files that could not be restored, if any;
* final recommendation for manual investigation.

The final log must remain after rollback.

## Failure report files

Failure reports must be written under:

```text
workflow/failures/
```

Use this naming pattern:

```text
workflow/failures/maintenance-step<index>-failure.md
```

Each failure report must contain:

* failed step file;
* failed action;
* files changed before failure;
* validation command or check that failed;
* exact error output where available;
* suspected root cause;
* rollback recommendation;
* required fix to include in the next maintenance regeneration;
* whether execution can safely resume after regeneration.

The failure report must be specific enough for the maintenance workflow to regenerate corrected steps without rediscovering the issue from scratch.

## Rollback rules

Rollback is required before the fifth attempt when:

* a step partially modified files and validation failed;
* forbidden files were modified;
* the repository is left in an inconsistent state;
* later maintenance regeneration depends on clean input files.

Before the fifth attempt, rollback must restore files from:

```text
workflow/backups/step<index>/
```

Rollback is required after a fifth failed attempt regardless of which step failed.

After the fifth failed attempt, rollback must restore all changed files from:

```text
workflow/backups/initial/
```

The fifth-attempt rollback must restore the repository to the state it had before unattended upgrade execution began.

Rollback must not remove the failure report.

Rollback must not remove the final unattended upgrade log.

Rollback must not remove generated maintenance files after a fifth failed attempt unless they are themselves restored from the initial-state backup as changed tracked files.

After rollback, verify that the restored files match the relevant backup manifest.

## Maintenance regeneration after failure

After creating a failure report for any failed attempt before the fifth attempt, run the maintenance workflow again.

The regenerated maintenance workflow must use:

* `workflow/description.md`;
* `workflow/maintain.md`;
* `workflow/versions.md`, if still valid;
* the failure report file;
* the current repository state after rollback or after the chosen safe failure state.

The regenerated maintenance files must include the detected issue and the required fix.

The regenerated files must replace:

```text
workflow/maintenance-plan.md
workflow/maintenance-scaffold.md
workflow/maintenance-step<index>.md
```

`workflow/versions.md` must also be updated if the failure was caused by incorrect version data.

After regeneration, unattended upgrade execution must restart from the new `workflow/maintenance-step1.md` as the next numbered attempt.

Do not continue from the previously failed step unless the regenerated maintenance files explicitly prove that all previous steps remain valid and already satisfied.

If the fifth attempt fails, do not regenerate maintenance files again.

## Completion cleanup

After all maintenance steps complete successfully and final validation passes, remove generated unattended-maintenance files.

Remove:

```text
workflow/versions.md
workflow/maintenance-plan.md
workflow/maintenance-scaffold.md
workflow/maintenance-step<index>.md
workflow/backups/
workflow/failures/
```

Do not remove:

```text
workflow/description.md
workflow/maintain.md
workflow/unattended-upgrade.md
AGENTS.md
README.md
```

Generated files must be removed only after successful completion.

If an attempt fails before the fifth attempt and regeneration is possible, keep generated files, backups, and failure reports for the next attempt.

If the fifth attempt fails, keep generated files, backups, failure reports, and `workflow/unattended-upgrade-failure.log.md` for inspection after restoring changed repository files to their initial state.

## Final validation

Before cleanup, run the strongest available final validation for the repository.

Final validation should include:

* checking the final diff;
* checking Dockerfile syntax or build planning;
* checking workflow YAML validity;
* checking image tag policy alignment;
* checking PHP version policy alignment;
* checking Debian baseline policy alignment;
* checking that no generated workflow-maintenance artifacts are required for normal repository operation.

If final validation fails, treat it as a failure of the last completed step and follow the failure handling process.

## Completion result

The unattended upgrade flow succeeds only when:

* every maintenance step executed successfully in order;
* every per-step validation passed;
* final validation passed;
* generated maintenance files were removed;
* the repository contains only the intended source, Docker, workflow, and documentation changes;
* no rollback data is required to understand the final repository state.

The unattended upgrade flow fails permanently when:

* five attempts have been used;
* the fifth attempt fails;
* `workflow/unattended-upgrade-failure.log.md` has been created;
* all changed files have been restored from `workflow/backups/initial/`;
* rollback verification has completed.
